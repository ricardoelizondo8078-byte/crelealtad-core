# AUDITORÍA UI ACTUAL — 31 JULIO 2026

## Alcance revisado

- Estructura completa del repositorio.
- Aplicación móvil React Native / Expo.
- Componentes de `apps/mobile/src/components/ui`.
- Tokens de `apps/mobile/src/theme/tokens.ts`.
- Pantallas de grupos, expedientes, solicitantes, solicitudes y documentos.
- Documentación de diseño y UX existente.
- Compilación TypeScript mediante `npx tsc --noEmit`.

## Resultado general

La aplicación compila correctamente y existe una base reutilizable funcional. El problema de continuidad visual se origina porque esa base todavía no controla todos los elementos visuales. Las pantallas comparten el encabezado, la barra de título y algunos controles, pero continúan definiendo directamente gran cantidad de estilos y patrones de interacción.

## Hallazgos principales

### 1. Documentación duplicada y con diferente nivel de precisión

Existen reglas en:

- `14_DESIGN_SYSTEM.md`
- `15_UI_UX_STANDARDS.md`
- `docs/project/15_UI_UX_STANDARDS.md`
- `apps/mobile/src/components/ui/README.md`

La intención es consistente, pero falta una autoridad técnica única con contratos de componentes, scroll, selección múltiple, estados y criterios de aceptación.

### 2. Tokens insuficientes

`tokens.ts` define colores neutrales, tres temas de módulo, tipografía, espaciado, radios y sombra. Todavía faltan:

- estados operativos tipados;
- tamaños táctiles;
- layout;
- iconos;
- niveles de elevación;
- variantes de superficie;
- estados de campos;
- tokens de feedback.

### 3. Valores visuales directos

Se encontraron colores, tamaños y valores arbitrarios directamente en componentes y pantallas, especialmente en:

- `ExpedienteDetailScreen.tsx`
- `DocumentosScreen.tsx`
- `SolicitudFormScreen.tsx`
- `SelectorField.tsx`
- `StickySectionHeader.tsx`

Esto permite que dos módulos representen el mismo concepto de forma diferente.

### 4. Componentes compartidos demasiado básicos

`Card`, `PrimaryButton`, `SecondaryButton` y `FormField` son útiles, pero no cubren variantes, carga, iconos, estado, accesibilidad avanzada ni contratos de dominio.

### 5. Patrones de scroll no normalizados

- `ScreenContainer` puede crear un `ScrollView` genérico.
- Otras pantallas crean su propio `ScrollView`.
- Listas potencialmente crecientes utilizan composición manual en lugar de `FlatList` o `SectionList`.
- No existe una taxonomía de scroll por tipo de pantalla.

### 6. Selección múltiple sin componente oficial

`SelectorField` resuelve selección simple mediante chips o modal. No existe contrato compartido para selección múltiple, límites, aplicar/cancelar, contador o búsqueda.

### 7. Pantallas de gran tamaño

`SolicitudFormScreen.tsx` tiene aproximadamente 1,900 líneas y `DocumentosScreen.tsx` más de 600. En ellas conviven:

- consulta de API;
- transformación de datos;
- autoguardado;
- validaciones;
- navegación;
- secciones del formulario;
- modales;
- estilos.

Esto hace más difícil preservar el formato y probar cambios sin regresiones.

### 8. Navegación temporal

La navegación principal se maneja mediante estado local en `src/App.tsx`. Es adecuada para prototipo, pero al crecer los módulos aumentará el riesgo de flujos inconsistentes. Deberá evaluarse una navegación tipada centralizada cuando el alcance funcional lo requiera.

## Fortalezas actuales

- Monorepo claro con API y móvil.
- Uso de TypeScript.
- Tema por módulo ya iniciado.
- Componentes UI centralizados.
- Encabezado y barra de título reutilizados en las pantallas principales.
- Principios UX alineados con el perfil de asesora en campo.
- Orden funcional del formulario largo ya considerado.
- Compilación móvil sin errores TypeScript al momento de la revisión.

## Recomendación inmediata

No agregar un nuevo módulo visual antes de:

1. aprobar `16_UI_COMPONENT_STANDARD.md`;
2. ampliar tokens;
3. crear componentes de estado, lista, selección múltiple y estados de pantalla;
4. migrar al menos una pantalla de cada plantilla como referencia;
5. incorporar el checklist UI a todos los prompts de Codex.

## Pantallas recomendadas como referencia después de migración

- Lista: `ExpedientesListScreen`.
- Detalle: `ExpedienteDetailScreen`.
- Formulario corto: `CreateGroupScreen`.
- Formulario largo: `SolicitudFormScreen`.
- Documentos: `DocumentosScreen`.

Estas pantallas sólo deberán considerarse referencia una vez que cumplan el nuevo estándar.
